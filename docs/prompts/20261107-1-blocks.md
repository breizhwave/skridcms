# Blocks: duplicate, move and delete

*7 November 2026 · Claude Code (Opus 5.5) · commits `6b2a094` scan, `55b7f35` api, `8f09b0f` bar*

## Prompts

> can skrid cms allow creating or duplicating blocks ? and moving them around

The answer was "not yet, but it fits": the scanner already knows byte offsets, so duplicating, moving and deleting
can be pure byte operations, like saving a text. Then:

> yes please, do it the best way, document it in docs via prompts and specific github commits in skrid folder

## What it does

In **Edit texts**, a click anywhere selects the nearest **block** around it: a dashed violet frame and a small
toolbar.

```
 ┌ div.card ── ↰ │ ↑ ↓ ⧉ 🗑 ┐
```

| Button | Effect |
| --- | --- |
| `div.card` | the selected block (tag and first class) |
| ↰ | select the block around it (li → ul → section…) |
| ↑ ↓ | swap with the previous / next block in the same parent |
| ⧉ | duplicate: the copy goes right after it, is selected, and its first text is active with all its text selected, so you type straight over it |
| 🗑 | delete, after a confirmation in the toast |

Each operation is written to the file at once. Texts still being edited are saved first, so nothing is lost. Then
the page reloads, because the numbering of texts and blocks changes, and the toast offers **Undo**.

**Creating** a block means duplicating a similar one and rewriting it. The new card, list item, stat or section
keeps the site's own markup and classes, which no template could do.

## What counts as a block

The scanner (`lib/scan.php`, `skrid_blocks()`) records an element as a block when all of these hold:

- its tag is in `SK_BLOCK`: section, article, aside, header, footer, nav, div, p, h1–h6, ul, ol, li, dl, dt, dd,
  table, tr, figure, blockquote, pre, details, fieldset, address, hgroup, menu. An `<a>` that wraps block content,
  like a card link, counts too;
- it is clean (explicit end tag), so an `<li>` closed implicitly is not a block;
- it is in the editing zone, the same zone as the texts (inside `<main>`, or the body minus the site's
  header/footer/nav), and outside forbidden ancestors (form, svg, button…);
- it neither contains nor touches PHP code.

For each block the scan gives `start`, `open_end`, `end` (just after `</tag>`), `parent` (the enclosing block),
and `prev` / `next` (the neighbouring block in the same parent element). A move never crosses PHP code: it could
carry a block in or out of an `if` or a loop, so a gap containing PHP gives `prev`/`next = null`.

The page sent to the browser gets `data-skrid-block="K"` next to `data-skrid="N"`, attributes only.

## Byte operations (`skrid_block_op`)

| Op | Bytes |
| --- | --- |
| duplicate | insert `sep + copy` right after the block. `sep` is the whitespace in front of the original (`\n    `, a space, or nothing), so the copy sits on its own line with the same indentation, or inline like its siblings |
| delete | remove the block **and** the whitespace in front of it, so the line goes away cleanly |
| up / down | `[A][gap][B]` → `[B][gap][A]`. Whatever sits between them (an `<hr>`, a comment) stays in place |

Duplicate then delete, and up then down, give back the exact original bytes. Nothing is re-serialised.

**Ids.** A copy must not repeat the original's ids (anchors such as `#flow`, `label for`). Every `id` in the copy
becomes `id-2` (or `-3`… if that is taken), and the references to it **inside the copy** follow: `for`,
`headers`, `list`, `aria-labelledby|describedby|controls|owns`, `href="#…"`.

## API

```
POST api.php?action=block   {page, hash, block: K, op: duplicate|up|down|delete}
→ {ok, hash, block: index of the copy / moved block (null after delete), backup, count}
```

- The hash is required (409 otherwise): block numbers only mean something on the file the bar was served from.
- A change to a PHP page's code is refused, like for `save`.
- Backup before writing; `sk_write()` now returns the backup's name. Logged as
  `{"a":"block","op":"duplicate","tag":"li"}`, and shown in *Admin › Activity* as "bloc dupliqué (li)".
- **Undo** = `restore` with that backup **and the current hash**. `restore` now accepts an optional hash, so an
  undo never overwrites a change made after it. *Admin › History* still restores without one.

## Bar (`assets/bar.js`)

- The frame and the toolbar live in the shadow DOM, like the rest of the bar, so the site's CSS never touches them
  and nothing is written into the page's own styles.
- The toolbar goes above the block on the right, under it if the text toolbar is in the way, and inside the block
  at the top right if neither fits.
- After the reload, `sessionStorage['skrid-after']` brings back the scroll position, the selection, the message
  and the Undo.
- In Edit mode, links inside blocks are not followed; Browse mode follows them. Escape deselects.
- Several elements with the same `data-skrid-block`, which happens with HTML repeated by a PHP loop, are left
  without block tools, like repeated texts.

## Tests

```sh
php tests/block_test.php /path/to/site [--list fr/page/index.html]   # fixed cases + every block of every page
php tests/scan_test.php  /path/to/site                               # mark/unmark now strips data-skrid-block too
```

`block_test.php` runs, for every block of every page: duplicate → delete the copy = original; up → down =
original; the copy adds exactly its own blocks and texts and repeats no id. Run on wave2027, levenez-musik,
emvodmeur-studio, skrid-cms, youlvat and wave2027/public: **127 pages, 28 488 operations, 0 failures**. `--list`
prints the block tree with ↑ ↓ where a move is possible.

Browser check (Playwright on a copy of the site, youlvat case study):

1. Clicking a stat selects `dd`, and ↰ selects its `div.flex` row.
2. Duplicate: the copy is written and its "24" is active. Typing 99 + Ctrl+S saves it, and the original row is
   still there.
3. Moving the copy up changes its place in the file; Undo gives back the exact bytes.
4. Delete asks first and nothing changes before confirming. Afterwards the file is byte-identical to the start.
5. Links inside blocks don't navigate in Edit mode; on the first block ↑ is disabled; a file changed behind the
   bar's back gives a 409 with Reload; Browse mode shows no block tools.

## Not done (yet)

- Header and footer blocks are still out of reach, waiting for the "apply to all pages in this language" plan
  (see CLAUDE.md). The same mechanism will work for repeated blocks.
- No drag and drop and no moving to another parent: only ↑ ↓ among siblings. That keeps every change a simple
  byte swap.
- No "insert a new empty block" from a template list: duplicating covers it without inventing markup.
